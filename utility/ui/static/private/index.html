How the private runner seal works

      
The finished seal gives you the only secret key that can unlock this runner. PortaBase keeps administrative control of the cloud service so we can maintain billing and terminate the runner, but the key is never stored in the PortaBase account system.

      

        
YOU CANUnlock and operate it
Use your recovery key to open the private dashboard, release a scheduled job, review local history, and recover a capsule.

        
PORTABASE CANStop or terminate it
We can validate the subscription, receive safe status, and terminate the cloud resource. Those controls do not provide the customer key.

        
PORTABASE CANNOTOpen or run it while sealed
Without your key, we cannot open its private state, read Supabase credentials, start a backup or replay, or decrypt a capsule.

      

      
Why the warning is shown now
This development build has the isolated loopback interface and private storage boundary, but its stored credential file is not encrypted by a customer key yet. An infrastructure administrator could still read it. The runner must not display “Sealed” until customer key encryption and denial checks pass.

      
      
If the recovery key is lost, PortaBase cannot recreate it. Keep the recovery copy outside the runner.

      
    

  
  
    

    

      
Technical boundary

      
How the customer-controlled runner works

      
This view exposes the engineering detail intentionally hidden from the guided setup. It distinguishes the current development build from the controls the sealed Linux runner must prove before release.


      

        
Execution path

        

          
1Browser
Renders a page served by the runner, accepts the four setup values, filters inventory, and displays progress. It does not perform the backup.

          
2Linux runner
Connects to Supabase, inventories data, captures selected content, builds the archive, encrypts the capsule, and performs recovery.

          
3Customer vault
Receives the encrypted capsule in customer-controlled storage. Recovery requires the capsule and its separate passphrase.

Current build: the credential file has restrictive file permissions, but it is not yet encrypted with a customer-held recovery key. A host administrator could read it. That limitation is why the runner is marked Seal not verified.

      


      

        

          
Network boundary

          
    
            
  • The current development dashboard binds to 127.0.0.1 and requires a random launch token.
    • 
            
  • The production design permits runner-originated connections to the bound Supabase project, the customer vault, and PortaBase subscription and status endpoints.
    • 
            
  • Supabase credentials, passphrases, inventory names, object paths, and diagnostic logs are excluded from PortaBase telemetry.
    • 
            
  • Outbound-only production networking remains a deployment requirement and is not proven by this Windows preview.
    • 
          

        

        

          
Storage boundary

          
    
            
  • Durable: configuration, SQLite inventory, selection history, and local evidence.
    • 
            
  • Scratch: captured data, archive construction, and encrypted-output overlap during a job.
    • 
            
  • The UI reports capacity only from the Linux runner filesystem. It refuses to present the operator workstation disk as runner capacity.
    • 
            
  • Scratch deletion does not replace capsule encryption or durable-state protection.
    • 
          

        

      


      

        

          
Evidence and provability

          
    
            
  • Runner-local SQLite records inventory revisions, selections, and operational events.
    • 
            
  • Capsule hashes and byte counts can prove which encrypted artifact was produced and delivered.
    • 
            
  • A fixed telemetry allowlist limits outbound status to job state, phase, duration, counts, verification results, and capsule hashes.
    • 
            
  • Provider logs, network-flow evidence, immutable audit retention, and negative access tests are needed to support stronger administrative-access claims.
    • 
          

        

        

          
Release proof still required

          
    
            
  1. Encrypt credentials and private SQLite state with a customer-held recovery key.
    2. 
            
  2. Demonstrate that PortaBase administration cannot unlock state or start a job without that key.
    3. 
            
  3. Deploy the real Linux runner with durable state and bounded scratch storage.
    4. 
            
  4. Prove outbound network restrictions and subscription-key refusal behavior.
    5. 
            
  5. Complete a backup, capsule verification, isolated restore, cutover, and rollback drill.
