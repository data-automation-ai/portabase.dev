What happens if I don't set a target project? Capsule-only restore

Uncheck "Also restore automatically into a target project" above and the destination boxes disappear — the encrypted capsule still goes to your configured storage destination (S3, Dropbox, local disk, etc.) every time, you just restore it yourself when needed:

ContainsWhat it isWhere it lands
Database backup fileA full dump of your Postgres databaseInside the capsule
Edge Function DDLsThe source/definition of every captured Edge FunctionInside the capsule
Binary objectsEvery file from the selected Storage bucketsInside the capsule

How to get it back out, later, yourself

  1. Find the finished capsule at your configured destination — for example, an object in your S3 bucket (under the prefix set in this runner's config), or a file in the Dropbox/Google Drive folder you pointed it at. It is a single opaque, encrypted file; nothing about it is readable without your capsule passphrase.
  2. Download that file to any machine with this runner's CLI installed (it does not have to be this runner — the capsule and the passphrase are enough).
  3. Run the CLI's restore command against it with your capsule passphrase. That decrypts the capsule and unpacks the database backup file, the Edge Function DDLs, and the binary objects into plain files on disk.
  4. From there: load the database backup file into any Postgres instance (a new Supabase project, or your own server), redeploy the Edge Functions from their DDLs, and copy the binary objects into whatever Storage/bucket you want them in. None of this requires PortaBase or an internet connection — it's your data, your passphrase, your choice of destination.

Choosing this means PortaBase never automates the restore step for you. That's the trade-off for not configuring a live target project.

How the private runner seal works

      
The finished seal gives you the only secret key that can unlock this runner. PortaBase keeps administrative control of the cloud service so we can maintain billing and terminate the runner, but the key is never stored in the PortaBase account system.

      

        
YOU CANUnlock and operate it
Use your recovery key to open the private dashboard, release a scheduled job, review local history, and recover a capsule.

        
PORTABASE CANStop or terminate it
We can validate the subscription, receive safe status, and terminate the cloud resource. Those controls do not provide the customer key.

        
PORTABASE CANNOTOpen or run it while sealed
Without your key, we cannot open its private state, read Supabase credentials, start a backup or replay, or decrypt a capsule.

      

      
Why the warning is shown now
This development build has the isolated loopback interface and private storage boundary, but its stored credential file is not encrypted by a customer key yet. An infrastructure administrator could still read it. The runner must not display “Sealed” until customer key encryption and denial checks pass.

      
      
If the recovery key is lost, PortaBase cannot recreate it. Keep the recovery copy outside the runner.

Technology used: AWS

        
When the destination for an encrypted capsule is configured as Amazon S3, here is exactly what that means and doesn't mean:

        

          
PieceWhat it doesWhat reaches your browser

          
Amazon S3Durable object storage that holds the finished, already-encrypted capsule file(s). S3 itself never sees plaintext — it stores opaque ciphertext bytes like any other object.Nothing; uploads happen runner-to-S3 directly

          
AWS access keysUsed only by the Linux runner process to authenticate the upload (PutObject) to the configured bucket/prefix.Not sent; keys live in runner environment variables only

          
Bucket ownershipEither a bucket in your own AWS account (you hold the keys and the bill) or a PortaBase-managed bucket, depending on how this runner's destination is configured.Shown as a destination kind only — bucket name/prefix stay private to the runner's config

        

        
S3 provides durability and access control for the stored object; it is not itself what keeps the data private — the AES-256-GCM encryption performed by the runner before upload is what does that. A party with only S3 read access, lacking your capsule passphrase, holds unreadable ciphertext.

      


      

        
Owning the runner vs. seeing inside it

        
PortaBase's cloud account is the one that provisions, bills, and can start, stop, or terminate this runner's compute resource. That is a real, meaningful form of ownership — and it is deliberately kept separate from the ability to read anything running on it.

        
Think of it like renting a tent at a campground. We — the campground — own the land and own the tent itself. We can see the tent standing there, bill you for the site, and take the tent down once you check out. But once you're inside with the flap zipped shut, that's it: we have no window, no second key, no way to see what you brought in or what you're doing in there. Owning the tent and the ground it sits on is not the same thing as being able to see inside it once it's zipped.

        

          
ControlPortaBase accountYou

          
Provision / bill / terminate the compute resourceYes — this is infrastructure ownership, same as any cloud billNo

          
Start or stop the runner processYes, via the subscription/control planeYes, from this private interface

          
Read Supabase credentials, the capsule passphrase, or inventory namesNo — these never leave this runner's private stateYes — you entered them here

          
Decrypt a capsule or read its contentsNo — requires your passphrase, which PortaBase does not holdYes

        

        
Current build caveat: right now, the zipper doesn't actually lock. This development build's private state file is not yet encrypted with a customer-held key, so campground staff with direct access to the tent pole — a host administrator with direct machine access — could currently still unzip the flap and read what's inside. The separation described above is the architecture we are building toward, not yet a proven guarantee. That's exactly why this runner is marked "Seal not verified": we won't call the tent "zipped and sealed" until that customer-held-key encryption, and the denial checks in the release-proof list below, actually pass.

        
Bottom line: once customer-held-key encryption ships, portabase.dev — and anyone else — will be unable to read or access your Supabase secrets. The runner itself will not even run without your key: it can sit anywhere, but its credentials and everything in its internal storage will be encrypted with that key, so execution requires it too.

What if I lose the encryption key for my runner?

        
There is no recovery option. Nobody — including PortaBase — can get back into a runner once its key is lost.

        
You can always create a new runner from your portabase.dev account. On the new runner you will need to re-enter your Supabase credentials and run a fresh inventory probe.

        
The manifests and logs kept inside the old runner are lost along with it — they live only in that runner's own encrypted local state. In practice this means your next backup starts over as a full backup: an incremental backup depends on the old runner's local history to know what changed, and that history no longer exists.

        
Keep your key somewhere durable outside the runner. There is no password-reset flow for it.

      


      

        
        
      

    

  
  
    

    

      
Verify it yourself

      
Verifiability

      
This page is the only code running in your browser for this runner. You do not have to take that on faith — you can check it yourself with tools already built into your browser.


      
Think of it like watching a restaurant kitchen through a glass wall instead of being told "trust us, it's clean back there." You don't need to be a chef to look through the glass and see for yourself that nothing shady is happening — you can watch exactly what goes in and what comes out. The sections below are that glass wall: a quick look tells most people what they need to know, and if you do know how to cook, the same glass wall lets you check the actual technique, not just the vibe.


      

        
What the hash proves

        
Every asset this page loads (/app.js, /app.css, this HTML) can be hashed and compared against the published source so you can confirm the bytes you downloaded match a specific, reviewable version. A matching hash tells you which exact code you received; it does not by itself prove that code is safe or bug-free — that still requires reading it or trusting a review of it.
